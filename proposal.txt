         Project Title
         Intent-Gated Data Transformation Agent

         Domain and Target User
         Domain: Data engineering and analytics
         Target users: Data analysts, data engineers, and developers who use LLMs to generate or
         automate data transformations.

         Problem Statement
         LLMs are increasingly being used to generate Python code for common data transformations
         such as filtering, deduplication, missing-value handling, type conversion, and column
         transformation. Although the generated code may execute successfully, it can still make changes
         that were not requested by the user. For example, when a user asks to remove duplicate
         customers, an LLM may accidentally remove valid records or modify unrelated columns while
         producing code that runs without any error. Existing data-quality approaches commonly check
         properties such as schema validity, missing values, uniqueness, and value ranges, while recent
         LLM-based data-cleaning systems also use profiling, execution-based checks, and repair.
         However, these checks do not directly answer whether the actual changes made by a
         transformation match what the user intended to change and whether unrelated data was
         preserved. Our project addresses this by representing each transformation request as an explicit
         intent contract describing both the properties that should change and the properties that must
         remain unchanged. After executing the generated transformation, the system compares the
         before-and-after datasets against this contract and detects semantic violations even when the
         generated code executes successfully. If a violation is detected, the system can attempt a
         targeted repair and verify the result again.

         Research Question

         Does an intent contract that specifies what must change and what must be preserved improve
         the detection of silent semantic errors in LLM-generated data transformations compared with
         conventional data-quality checks?

         Hypothesis
         An intent-based verification mechanism will reduce the number of incorrect transformations
         that are silently accepted, while maintaining a low false-rejection rate for correct
         transformations.

         Why the Problem Matters in This Domain
         Incorrect transformations can silently corrupt datasets even when the generated code runs
         without errors. Such errors can propagate into dashboards, statistical analysis, machine-learning
         pipelines, and business decisions. A reliable transformation agent therefore needs to verify not
         only whether the output is technically valid, but whether it performs the specific transformation
         requested by the user.

         What Is Missing in Existing Approaches
         Traditional data-quality systems provide explicit checks for properties such as uniqueness, null
         values, schema, distributions, and cross-column integrity. Recent LLM-based data-cleaning
         agents add profiling, execution, and conservative repair, so simply adding an invariant checker
         would not be sufficiently novel. Our focus is narrower: intent compliance of the transformation
         itself. We explicitly represent both what should change and what should be preserved, then
         measure whether the agent introduces unintended changes even when ordinary data-quality
         checks pass.

         Three Capabilities Used
         1. Fine-tuning
         A small open model will be fine-tuned with LoRA/QLoRA to convert natural-language
         transformation requests into a structured intent contract.
         Why needed: The system needs consistent structured representations of transformation intent.
         Fine-tuning allows the parser to learn the fixed contract format and predicate vocabulary used
         by the verifier.

         Intent Contract
         The intent contract will use a small closed vocabulary of machine-checkable predicates rather
         than arbitrary free-text descriptions.
         The core predicate vocabulary will include:
               row_count


               rows_removed_where


               duplicate_count

               null_count


               column_values_unchanged

               columns_unchanged


               column_dtype


         A gold intent contract is a trusted, human-prepared description of what the system is supposed
         to change and what it must preserve for a particular user request.
         Think of it as the answer key for your fine-tuned model.
               column_value_relation


         Each predicate will have a deterministic verifier implementation. Conditions will use a normalized
         structured format rather than free-form strings.
         Example:

           {
               "must_change": [
                {
                    "type": "rows_removed_where",
                    "target": "price",
                    "condition": {

                           "operator": "<",
                           "value": 0
                       }
                   }
               ],
               "must_preserve": [
                   {
                       "type": "column_values_unchanged",
                       "target": "customer_id"
                   },
                   {
                       "type": "columns_unchanged",
                       "target": ["name", "host_id"]
                   }
               ]
           }




         Contract matching will be deterministic and based on normalized fields such as:
         predicate type + target + normalized condition/value
         This allows the intent parser to be evaluated using standard Precision, Recall, and F1 without
         using an LLM judge.

         Expected Novelty
         The novelty of the project is not simply using LLMs for data cleaning, using invariants, or adding
         execution-based verification. These approaches already exist in related data-quality and agentic
         data-cleaning systems.
         The proposed contribution is the use of a bidirectional, intent-conditioned transformation
         contract.

           What the transformation is expected to change
                           +
           What the transformation is required to preserve




         The evaluation will specifically test silent semantic errors that can pass ordinary data-quality
         checks. The project will compare intent-based verification against conventional invariant
         checking and no verification, rather than claiming that data-quality validation or agentic data
         cleaning itself is new.

         Primary Evaluation Tasks
         We will manually specify approximately 60–80 transformation tasks over these real datasets.
         The tasks will be restricted to five transformation types:
             filtering
             deduplication
             missing-value handling
             type/format conversion
             column transformation
         The task requests will be hand-written or paraphrased and kept separate from the automatically
         constructed examples used for fine-tuning.

         Secondary External-Validity Evaluation
         We will additionally evaluate on approximately 20–30 selected DS-1000 Pandas problems.
         Only problems with clear and measurable must-change and must-preserve semantics will be
         selected. The DS-1000 results will be reported separately from the real-dataset task results.

         Ground Truth
         For each evaluation task, we will prepare the correct reference transformation and a gold intent
         contract specifying what must change and what must remain unchanged. We will compare the
         model-generated contract against this gold contract to measure its accuracy.

         Oracle-Contract Ablation
         An additional ablation will provide the verifier with the gold contract instead of the parser-
         generated contract.

           Gold Contract → Transformation → Same Intent Verifier




         This keeps the verifier unchanged and isolates the effect of contract-generation errors.
         The performance gap between the predicted-contract and gold-contract settings estimates how
         much of the overall error comes from misunderstanding user intent during contract generation.

         Primary Verification Metrics
             Silent semantic error rate: incorrect transformations accepted by the system.
             Intent-violation recall: percentage of incorrect transformations detected.
             False rejection rate: percentage of correct transformations incorrectly rejected.

         Repair Metrics
             Repair success rate: percentage of detected errors successfully repaired.
             Final transformation accuracy: percentage of tasks producing the correct final dataset.
             Average repair attempts: average number of repair iterations used.
             Improvement from repair: change in correctness before and after enabling the repair loop.

         Compute Plan
             Base model: small open model such as Qwen2.5-1.5B/3B or a similar small open model.
             Fine-tuning: LoRA/QLoRA on approximately 3,000–5,000 automatically constructed intent
             examples.
             Training compute: approximately 2–4 GPU hours on a single 16–24 GB GPU.
             Inference: primarily local inference using open models.
         The project will prioritize small/open models and local inference to keep the compute and API
         requirements low.

         Expected Risks and Fallback Plan
         Risk 1: Intent contracts may be too difficult to generate reliably.
         Fallback: restrict the project to the fixed set of transformation types and closed contract
         predicates.
         Risk 2: Some transformations may not have clear preservation properties.
         Fallback: remove ambiguous tasks and focus on transformations with measurable before/after
         effects.
         Risk 3: Gold intent contracts may contain annotation ambiguity.
         Fallback: have a second teammate independently annotate a sample, measure agreement, refine
         ambiguous contract definitions before final evaluation, and exclude tasks that remain ambiguous.
         Risk 4: The intent-based method may not outperform generic invariants on all tasks.
         Fallback: analyze which classes of silent semantic errors are specifically detected by intent
         verification, even if overall improvement is limited.
