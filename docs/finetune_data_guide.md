# Guide: collecting fine-tuning data for the intent parser (Phase 7)

## 1. What we need, in one paragraph

The fine-tuned parser (Qwen2.5-1.5B and 3B, QLoRA) learns one thing: **request + dataset schema → intent
contract** (JSON, vocabulary v1.0). We need **3,000–5,000 training examples** of exactly that, built on
**datasets that are not used in evaluation**, each one **checked automatically** with our own verifier. Most
examples are generated by a script from templates; a small model may paraphrase requests for variety.

Inputs and outputs must look exactly like what the parser sees at evaluation time:

```
INPUT (user message)                                    OUTPUT (assistant message)
Dataset: 344 rows, 8 columns.                            ```json
Columns (name: dtype, missing values):                   {"contract_version": "1.0",
- species: object, 0 missing                              "must_change": [
- bill_length_mm: float64, 2 missing                       {"type": "rows_removed_where", "target": null, "condition": {...}},
...                                                        {"type": "row_count", "target": null, "op": "decreased"}
First 3 rows (CSV):                                       ],
species,island,bill_length_mm,...                         "must_preserve": [ ... ]
Adelie,Torgersen,39.1,...                                }
Request: Drop the penguins that weigh under 3500 g.      ```
```

You only write the **request**, the **contract** and a **reference solution** per example.
`finetune/data_gen/build_sft.py` produces the exact chat format above (system prompt version p1-v2, recorded in the adapter).

## 2. Hard rules (the evaluation is invalid if these are broken)

| Rule | Why | Checked by |
|---|---|---|
| **No evaluation datasets.** Never use Adult, Airbnb, NYC Taxi or Titanic, or another copy of them. | Otherwise the parser memorises the test schemas (README G11). | `check_examples.py` (path and column set) |
| **No evaluation requests.** Don't open `eval/tasks/` while writing templates, and never copy or adapt a request from there. | Same phrasings in training and test inflate the result. | `check_examples.py` (5-gram overlap, similarity) |
| **No gold contracts as training labels.** Don't copy contracts from `eval/tasks/`. | Same reason. | Review |
| **Vocabulary v1.0 only.** The 11 predicates and fields in `docs/eval_set_and_contract_guide.md` §5. No new predicates or functions. | The verifier and every parser use one vocabulary. | `check_examples.py` (pydantic) |
| **Every contract follows the annotation rules** in the guide §6 (default preservation, null rule, non-vacuity, minimal-but-complete). | The parser must learn the same conventions as the gold contracts. | `check_examples.py` (reference passes, no-op fails) + review |

You **may** read `docs/eval_set_and_contract_guide.md` (the rules) and the **dev** tasks' contracts for format.
Don't read test tasks.

## 3. Step 1: pick 6–10 training datasets

Pick public tabular datasets with **different schemas** and a mix of column types: numbers, categories, text,
dates, some missing values, some duplicates. Suggestions (check each licence and record it):

| Dataset | Why it's useful |
|---|---|
| UCI Wine Quality | numeric columns, few categories; good for thresholds and derived columns |
| Palmer Penguins | categories + numbers + real missing values |
| UCI Bank Marketing | many categorical columns, `unknown` values like Adult's `?` |
| UCI Student Performance | categories, grades, yes/no columns |
| Diamonds | ordered categories (cut, color, clarity), prices |
| A movie / books / app-store dataset | text titles (strip/lower), dates, duplicates |
| A weather or air-quality dataset | dates, missing readings, sensor-error values |
| A retail / sales dataset | invoice dates, quantities, duplicate rows, negative values (returns) |

For each dataset:
1. Take a **fixed 500–1,500-row sample** and save it as `finetune/datasets/<name>.csv` (CSV, header row).
2. Write a one-page profile in `finetune/datasets/README.md`: source URL, licence, rows, columns, which columns
   have missing values, duplicates, special values, plus the sha256 of the CSV.
3. Keep **one or two datasets aside for validation** (whole datasets, not rows): they never appear in training.

## 4. Step 2: write patterns (templates)

A **pattern** is one kind of transformation with three linked parts: a request template, a contract template and a
reference-code template. A script fills them in with columns and values that fit each dataset.

Cover all five types, and inside each type, several patterns. Start with these (aim for 30–40 patterns in total):

| Type | Pattern ideas | Main predicates |
|---|---|---|
| filtering | numeric threshold; value in a list / not in a list; compound AND; compound OR; remove a group within a group ("private rooms in Manhattan under 60"); keep only; nulls in the condition (decide include/exclude) | `rows_removed_where`, `rows_retained_where`, `row_count`, `columns_unchanged` |
| deduplication | full-row duplicates; duplicates on a key; key = all columns except some; keep first; keep last | `duplicate_count` (+`keep`), `row_count`, `columns_unchanged` |
| missing_values | fill with a constant; fill with another column; replace a sentinel (`?`, `unknown`, `-1`, `0`) with missing; drop rows with a missing value in a column / any column | `column_value_relation` (+`where`), `null_count`, `column_values_unchanged`, `rows_removed_where` |
| type_conversion | to category; to ordered category with a given order; text → datetime; float → int; int → text; yes/no → bool | `column_dtype`, `column_value_relation` (`cast`), `null_count unchanged` |
| column_transformation | rename; new column from arithmetic (add/sub/mul/div); round; clip; lower/upper/strip; map values; drop a column | `columns_added`, `columns_removed`, `column_value_relation`, `columns_unchanged` |

Example pattern (filtering, numeric threshold):

```yaml
pattern: filter_numeric_threshold
applies_to: any numeric column C without missing values, threshold T with 5–60% of rows below it
request_templates:
  plain:     "Remove the rows where {C} is below {T}."
  casual:    "Get rid of anything with {C_words} under {T}."
  domain:    "Drop the {entity_plural} whose {C_words} is less than {T}."
  indirect:  "Only keep {entity_plural} with a {C_words} of at least {T}."
contract:
  must_change:
    - {type: rows_removed_where, target: null, condition: {column: C, op: "<", value: T}}
    - {type: row_count, target: null, op: decreased}
  must_preserve:
    - {type: rows_retained_where, target: null, condition: {column: C, op: ">=", value: T}}
    - {type: columns_unchanged, target: "*", except: []}
reference_code: |
  def transform(df):
      return df[df["{C}"] >= {T}].copy()
```

Rules for templates:
- **Several phrasings per pattern** (at least 4 styles: plain, casual, domain words, indirect/negated).
  Use human column words (`C_words`, e.g. "body mass" for `body_mass_g`) as well as exact names.
- **Values must come from the data** (real categories, thresholds that split the data), so contracts are non-vacuous.
- **Null cases on purpose**: when a column has missing values, generate both readings and say which one in the
  request ("including the ones with no value").
- Don't write requests that are ambiguous between two contracts.

## 5. Step 3: generate examples

Write `finetune/data_gen/generate_examples.py` (yours) that, for each dataset × pattern:
1. finds columns/values that fit `applies_to`,
2. fills the request (random style), the contract and the reference code,
3. writes one JSON line:

```json
{"id": "penguins_filt_0001", "source_dataset": "penguins", "data_file": "finetune/datasets/penguins.csv",
 "transformation_type": "filtering", "pattern": "filter_numeric_threshold", "style": "casual",
 "request": "Get rid of anything with body mass under 3500.",
 "contract": {"contract_version": "1.0", "must_change": [...], "must_preserve": [...]},
 "reference_code": "def transform(df):\n    return df[df[\"body_mass_g\"] >= 3500].copy()\n"}
```

Target: **4,000–6,000 raw examples** (some get dropped), balanced: about 20% per transformation type, no dataset
above 20% of the total, no pattern above 5%.

**Optional paraphrasing** with a larger model (e.g. Qwen2.5-7B on Kaggle): rewrite a request in different words,
keep the contract unchanged. Then check the meaning didn't change: re-parse the paraphrase with the template's
own logic or review a sample by hand. Mark these with `"style": "paraphrase"`. Keep them under ~30%.

## 6. Step 4: check every example (automatic)

```
.venv/bin/python finetune/data_gen/check_examples.py finetune/data/raw/*.jsonl --out finetune/data/checked.jsonl
```

Each example must pass all seven checks, otherwise it is dropped with a reason:

| Check | Meaning |
|---|---|
| data | not an evaluation dataset (path and column set) |
| schema | valid vocabulary v1.0 contract, only real column names |
| runs | reference code passes the safety checker and runs in the sandbox |
| passes | the reference output **passes** the contract (our intent verifier) |
| nonvacuous | returning the input unchanged does **not** pass |
| leakage | no shared 5-word phrase with any evaluation request, character similarity ≤ 0.75 |
| unique | no duplicate id or request text |

Read `finetune/data/checked.report.json`: the counts per type, dataset, predicate and style, and the reasons for
every dropped example. Fix templates that produce many drops (a bad template usually fails "passes").

## 7. Step 5: build the training files

```
.venv/bin/python finetune/data_gen/build_sft.py finetune/data/checked.jsonl --val-datasets <your held-out datasets>
```

Writes `finetune/data/sft_train.jsonl` and `sft_val.jsonl` (chat messages in the evaluation format) and
`sft_stats.json`. These are the files the QLoRA training script reads.

## 8. Step 6: hand review

Before training, read **100 random examples** (20 per type) and mark each OK / wrong contract / unnatural request.
If more than ~5% are wrong, fix the templates and regenerate. Save the review as `finetune/data/review.csv`.

## 9. Done when

- [ ] 6–10 training datasets saved with profiles, licences and checksums; validation datasets chosen
- [ ] 30+ patterns covering all 11 predicates, all 14 relation functions, all condition operators (incl. `in`, `not_in`, `any`, `not`) and all five types
- [ ] ≥ 3,000 examples pass `check_examples.py`; balance targets met (report)
- [ ] 0 leakage drops left unexplained; no evaluation dataset used
- [ ] 100-example hand review done, ≤ 5% wrong
- [ ] `sft_train.jsonl` / `sft_val.jsonl` built

## 10. Files

```
finetune/
├── datasets/            <name>.csv + README.md (sources, licences, sha256)        <- friend
├── data_gen/
│   ├── patterns/        one YAML per pattern (request templates, contract, code)  <- friend
│   ├── generate_examples.py                                                       <- friend
│   ├── check_examples.py   automatic checks (§6)                                  <- ready
│   └── build_sft.py        chat-format training files (§7)                        <- ready
└── data/                raw/*.jsonl, checked.jsonl (+report), sft_train/val.jsonl, review.csv
```

Questions about what a contract should say go to the rules in `docs/eval_set_and_contract_guide.md` §6.
If a request needs something the vocabulary can't express, **drop that pattern** rather than bending the vocabulary.
